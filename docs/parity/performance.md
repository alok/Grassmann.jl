# Performance parity matrix (key: performance)

Audit of Lean-vs-Julia performance for the Lean port at master `0ac54fdd` (2026-09-25). Read-only on the master checkout.

**Sources.** (1) `docs/PERF.md` and module docs (`Grassmann/Forms.lean`, `Grassmann/Composite.lean`, `Grassmann/Kernel/Plan.lean`); (2) a fresh run of the in-flight harness binary (`.claude/worktrees/wf_ca333ec6-97a-1/.lake/build/bin/bench`, master merged) against its Julia twins (`oracle/bench/*.jl` on that branch, results in the scratch `jl_*.json`); (3) today's reruns of the orphan benches `Bench/Grassmann/Products.lean`, `Tests/Cartan/Bench.lean`, `Tests/Composite/Bench.lean` (compiled against master's build products, scratch `parity/pb/`) and their Julia sides (`oracle/bench/grassmann_bench.jl`, `oracle/cartan/bench.jl`, scratch `composite_bench.jl`); (4) scratch probes of the dynamic layer (`DBench.lean` vs `dyn_bench.jl`) and of ComplexF64/`Float.ofInt` (`CBench.lean`); (5) generated C inspected for `Values.dot`, `ComplexF64.div` in an array loop, and the quaternion constructor.

**Machine / noise.** Apple M4 Max (12P+4E), Julia 1.13.0 + Grassmann 0.8.46, Lean 4.35.0-rc3. Load average ≈ 11–14 during the runs (other agents building): expect ±10–20 % noise; best-of-N minima are reported. Ratios are Lean ÷ Julia (>1 = Lean slower). Status: **SLOW** > 1.2×, **OK** 0.83–1.2×, **FASTER** < 0.83×, **SKIP** = one side has no counterpart, **UNMEASURED** = no benchmark.

## Root causes (codes used in the table)

| code | cause | fix |
|---|---|---|
| A | Allocation floor: every result is a fresh heap object (`FloatArray`, `Vector`, `Array`); ≈10–15 ns alloc+init+free per result, while Julia's isbits tuples live in registers (PERF.md 'copy of an operand' row: 10.9 ns Lean vs 0.68 ns Julia in ℝ3). | Destination-passing / exclusive-operand reuse for binary kernels (today only unary `m := ~m`); expression fusion (in-flight `Grassmann/Fuse`) so chains like `R*v*~R`, `a*b+c` allocate once; SoA batches (in-flight `Grassmann/Batch`) for bulk work; for layouts of ≤ 4 floats an unboxed `structure` register form (`Float` fields are stored unboxed in the ctor, and ctor/proj cancel when the consumer is inlined). |
| L | `Nat`-indexed structural loops (`lean_nat_sub/add/dec_eq` per step), bounds-checked `get!`/`set!`, `a[i]!` on `FloatArray` (out-of-line bounds-check lambda, PERF.md), `Nat` `/`/`%` per element, no unrolling for statically known small `n` (verified in the generated C of `Values.dot` at n=3). | `USize` loops with `uget`/`uset` and proofs (or `get!`/`set!` → `fget`/`fset` forms), nested loops instead of `/`/`%`, 4-way unrolled accumulators, elaboration-time unrolling for n ≤ 4/8 (same codegen idea as `Grassmann.Kernel.Codegen`). |
| B | Out-of-line runtime calls in scalar kernels: `lean_float_to_bits`, `lean_float_of_bits`, `lean_float_scaleb`, `lean_float_isnan` are `LEAN_EXPORT` functions (not `static inline`) in the 4.35 `lean.h`; `Int32`/`Int64` literals are closed terms read through atomic once-cells. | Upstream `static inline` versions of the bit casts/scaleb in `lean.h` (trivial `memcpy`; try in `~/lean4`), meanwhile arithmetic reformulations that avoid bit casts on the fast path, and `i64!`/`u64!` module-global literal macros like `f64!` (JuliaBase/FloatLit.lean). |
| I | `Float.ofInt`/`Float.ofNat`/`Nat.toFloat` go through `OfScientific` (measured today: 40 ns per `Float.ofInt` of a small Int; ≈8 µs for a Nat ≥ 2^63). | A `F64.ofInt` helper via `Int64.toFloat`/`UInt64.toFloat` (inline `lean_int64_to_float`) with a bignum fallback; replace the hot call sites. |
| P | Polymorphic boxing: `JuliaBase.Complex α` and `Float × Float`/`Float × Int` tuples box both floats at call boundaries and join points (generated C of a `ComplexF64.div` array loop: `lean_box_float` ×2 in every branch; a call to `ComplexF64.sqrt` allocates a ctor with two boxed floats). | A monomorphic `structure C64 where re im : Float` (scalar fields unboxed) for the Float kernels, CPS variants (`F64.sincosK` pattern) for multi-value returns, `@[inline]` wrappers. |
| D | Run-time interpretation instead of generated code: the dynamic layer replays Julia's loops (`Grassmann.Dynamic.Loops`) and maps entries with per-entry `Rat` coefficients and `Leibniz.basisRank` recomputation; plan lookups (≈50 ns) in fallback paths. | Dispatch `TA` kinds to the static typed kernels (generated at `Float`), precompute per-(V, op) `Float` sign/permutation tables, table-backed `binomsum`/`basisRank`. |
| S | No SIMD / array-of-pointers layout: `Array (Values Float n)` is an array of separate heap `FloatArray`s; field kernels run per point. Julia stores contiguous isbits arrays and LLVM vectorizes broadcasts (≈0.15–0.5 ns per element). | Flat/SoA storage (component-major `FloatArray`s) and plain `USize` loops that clang can auto-vectorize; whole-field generated loops. |
| N | Bignum-capable representations on hot paths: `BitVec (2^N)` (Nat-backed; values ≥ 2^63 are GMP objects), `Rat`/`Int` exponent vectors, `Nat` keys and counters. | Fixed-width `UInt64`/`Int64` representations (with proofs bridging to the spec types via `@[implemented_by]` or `UInt64.toBitVec`). |
| T | Text processing through `List Char`, `String` concatenation and exact `Nat` decimal arithmetic. | Byte-level scanning (`String.toUTF8`/iterators), `UInt64` digit arithmetic, Clinger / Eisel–Lemire fast paths with the exact path as fallback; precomputed label tables. |
| R | Laziness: Julia keeps ranges and range-valued fields lazy (O(1)); Lean materializes them. | Keep a lazy `range?` representation end to end; materialize on demand with a fast `Axis.get`. |
| K | Julia constant-folds per-type constants at compile time (planet parameters, conversion factors); Lean reads cached structures and recomputes at run time. | Specialize on literal systems (top-level `f64!` constants, `@[inline]` with constant args) or precompute tables at elaboration time. |
| C | Closed forms missing or replaced by series / multi-product paths (several kernel products and `Values` allocations per call). | Straight-line closed forms per space (generated like the product kernels), in-place accumulation. |
